What was fixed in v2

  • Assistant turns excluded from Memory.add() — v1 passed full conversations (user + assistant turns), causing llama3.2 to store verbatim assistant lines as facts (e.g. "Cloud-native stack! Any favourite tools?"). v2 filters to user-role messages only.
  • Both conversations merged into one Memory.add() call per user — v1 called Memory.add() twice per user, causing the second conversation's facts to be false-deduped against the first. v2 merges all user turns in a single call.
  • Result: 16 clean facts (was 21) in 14.7s (was 44.4s) — 5 fewer facts, 3× faster ingestion, zero assistant-line noise.

Key Observations

Token savings are consistent and real (23–81%). Even the lowest-saving query (M1, 23%) cuts nearly a quarter of the prompt. Cross-user query C3 achieves 81% savings because the naive baseline must include all 4 users' full history (411 tokens), while mem0 returns 3 focused facts (78 tokens).

Recall@3 is strong for user-scoped queries (avg 0.89 for BASIC+MEDIUM). For all 6 user-scoped queries (B1–M3), at least one of the top-3 memories contains the relevant keyword. The semantic distance model (nomic-embed-text COSINE) reliably finds the right fact when the query is scoped to a single user.

C3 (cross-user, P@3=0, R@3=0) exposes a real limitation. The query asks for users who combine engineering + healthy lifestyle. COSINE similarity with "software engineering + healthy lifestyle" returns engineering facts (Rust, fintech) with high similarity, but Charlie's marathon/meal-prep and Alice's hiking score lower — the embedding space separates these domains. Hybrid BM25+vector search or a two-step retrieval (first find engineers, then filter for health facts) would fix this.

Precision@3 is moderate (avg 0.37). Top-1 hits are almost always correct; positions 2–3 often contain adjacent but not exactly relevant facts (e.g. volunteering at a shelter surfacing alongside Kubernetes). This is expected with a small 16-fact store — more facts per user would improve intra-user ranking.

Ingestion is 3× faster in v2 (14.7s vs 44.4s). Merging conversations + skipping assistant turns reduces the number of Memory.add() calls from 8 to 4 and the LLM's deduplication work from ~10 comparisons to ~4.

Db2 VECTOR_DISTANCE() latency is excellent (40–56ms). With 16 stored vectors the query is near-instant. This will scale well as facts accumulate.
